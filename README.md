# 本地汇总份额防泄露判定器（leakguard）

业务每天以多种汇总格式（行份额、列份额、对角份额等线性整数等式）向外部复核方
开放数据。**每张表单独看都合规，不代表多次开放叠加后仍然安全**：外部复核方把
历次拿到的约束联立，可能唯一反推出本应隐藏的保护格。

本工具是一个 **纯 Python 标准库、本地运行、整数精确运算** 的判定器，输入合成的
整数上限、已批准披露记录和待批申请集合，输出：

- 保护格**仍有两个以上合法值** → 同时给出两张逐格可复核的整数表（见证表）；
- 保护格**被唯一确定** → 给出最小的已开放约束集合，以及三种互相独立的校验方法；
- 撤回区分「从未对外发布」与「已可被外部保存」，后者进入只增不减的外部台账，
  撤回不产生抵消；
- 两队同时申请、各自安全而组合不安全时，**按实际承诺顺序（order）裁决**，
  并提供顺序翻转的反事实演示；
- 多批互不相关的表按约束宇宙签名做增量缓存，计数器证明**只重新访问被触及的
  格子和约束**，未触及表本批次零访问。

无第三方依赖，Windows + Python 3.10+ 直接运行（开发环境为 Python 3.12）。

## 目录结构

```
leakguard/
  model.py       数据模型：表、线性约束、披露记录生命周期、访问计数器
  solver.py      有限域整数求解：区间传播 + MRV 回溯、min/max 定值判定、穷举
  certificate.py 最小约束子集提取 + 三种独立复核（新求解器/暴力枚举/手算指引）
  engine.py      判定引擎：台账、裁决、顺序处理、增量缓存与计数
  jsonio.py      JSON 场景载入与结果序列化
  demo.py        五个可复现演示场景（合成数据）
  cli.py         命令行入口
examples/
  scenario_sample.json   JSON 输入示例
tests/
  test_leakguard.py      19 项 unittest（含与独立暴力枚举的全子集对照）
```

## 快速开始

```bash
python -m leakguard.cli selftest     # 求解器 vs 独立暴力枚举的冒烟自检
python -m leakguard.cli demo         # 运行全部五个演示场景
python -m leakguard.cli demo --scenario 4
python -m leakguard.cli check examples/scenario_sample.json   # JSON 场景，输出 JSON 裁决
python -m unittest discover -s tests -v                       # 完整测试套件
```

`check` 的退出码：全部申请获批为 0，存在否决为 1，输入错误为 2，便于接入流水线。

## 演示场景一览（合成 2×2 整数表，上限 U=9，保护格 d）

| 场景 | 说明 | 结论 |
|---|---|---|
| 1 | 四种行/列份额逐日开放后再申请对角份额 | 前四份额下 d∈[0,4] 仍歧义；叠加对角份额后 d 被唯一确定为 2，否决 |
| 2 | 只开放一条行份额 | d∈[0,9]，给出两张合法整数见证表 |
| 3 | 撤回「未发布」与「已发布」记录 | 前者约束失效恢复歧义；后者留在外部台账，d 仍被确定，重新申请报冲突 |
| 4 | A/B 两队各自安全、组合不安全 | 按 order 串行裁决：先到者获批、后到者否决；翻转 order 结果随之翻转 |
| 5 | 五张互不相关的表分批申请 | 未触及表缓存命中、本批次零访问；重复请求零求解；对照关闭缓存访问量明显更大 |

## 核心语义

### 1. 定值判定与双见证

对每个保护格 x，求它在全部生效约束下的可行值集合的最小值与最大值：

- `min < max`：至少存在两个合法值。求解器分别给出取到 min 和 max 的两张
  **完整整数赋值表**，并由独立代码逐格检查域边界、逐约束代回等式，确认两张表
  都合法且保护格取值不同；
- `min == max`：保护格被唯一确定。判定基于单调谓词二分（大表）或一次穷举
  （小表，域组合数 ≤ 20000 时），两条代码路径在测试中互相校验。

### 2. 最小已开放约束集合

保护格被定值后，从全部生效约束中提取使其定值的最小子集：

1. **删除法**得到不可再删集合（删去任意一条都会破坏定值）；
2. 约束总数 ≤ 10 时，再按基数从小到大做组合搜索，证明**条数最少**
   （`minimum-cardinality`），否则仅保证不可再删（`irredundant`）；
3. 每条约束标注来源记录 ID（或 `pending-request`），可直接追溯是哪一次开放
   贡献了泄露。

### 3. 三种独立校验（互为冗余，防止单一实现出错）

- **全新求解器重算**：另建求解器、计数器清零后重新判定；
- **暴力枚举**：不走传播/回溯代码，对所有整数组合做笛卡尔积逐条代入
  （仅小表，组合数超 200000 自动跳过并标注）；
- **手算指引**：输出每条等式的整数展开与传播后整数域快照，复核人可逐值代入，
  全程只有整数加减乘。

### 4. 撤回的两种状态（不能互相抵消）

| 状态 | 含义 | 对约束宇宙的影响 |
|---|---|---|
| `approved_draft` | 已批准但**从未对外发布** | 生效中 |
| `published` | **已经对外发布**，外部可能已保存 | 生效中，进入外部台账 |
| `withdrawn_draft` | 撤回未发布记录 | 约束彻底失效，可重新申请 |
| `withdrawn_published` | 撤回已发布记录 | **内部停用展示，但外部台账保留、判定时仍计入** |
| `denied` | 申请被否决 | 不产生约束 |

外部台账是追加式的：任何曾为 `published` 的记录永远可查。对已发布过的同一约束
重新申请时，`republish_request` 会返回冲突记录 ID——撤回无法腾出重新开放空间。

### 5. 承诺顺序裁决

`adjudicate()` 把所有申请按 `order` 升序串行处理：每条申请在「当前已落账约束 +
本申请临时约束」上判定，通过才落账并影响后续申请。两队各自反事实单独申请都
安全、组合后才定值时，`order` 小的一方用掉安全余量并获批，另一方被否决。
`counterfactual_order()` 在同一份台账快照上独立模拟「假设某队先到」，
`scenario_two_teams_reversed` 演示交换 order 后裁决结果整体翻转。

判定不充分（回溯预算耗尽）或约束集不可满足时一律 **fail-closed 否决**。

### 6. 增量评估与访问计数

- 每张表的判定结果按「域边界 + 保护格 + 全部生效约束」的**签名**缓存；
- 记录落账/撤回只失效该表的缓存条目，其它表签名不变直接命中；
- `Counters` 分别记录格子访问、约束访问、搜索节点、求解调用次数；
  `TableVerdict.batch_delta` 是该表在**本批次**的增量（命中缓存时全为 0），
  与首次求解的历史计数严格区分；
- 场景 5 的实测对照：增量批次只求解 1 张表（4 次缓存命中），重复请求
  5 张表全部命中、零求解；关闭缓存的全量重评求解 5 张表，访问量约为 5 倍。

## JSON 输入格式

```json
{
  "node_limit": 200000,
  "tables": [{
    "table_id": "T1",
    "lower": 0,
    "upper": 9,
    "cells": ["a", "b", "c", "d"],
    "protected": ["d"],
    "rows": 2,
    "cols": 2,
    "cell_bounds": {"a": [0, 5]}
  }],
  "records": [{
    "record_id": "PUB-C1",
    "team": "外部复核方",
    "order": 1,
    "state": "published",
    "constraint": {
      "table_id": "T1",
      "name": "C1:行和R1=7",
      "rhs": 7,
      "terms": {"a": 1, "b": 1}
    }
  }],
  "requests": [{
    "request_id": "REQ-5",
    "team": "业务方B",
    "order": 5,
    "constraints": [
      {"table_id": "T1", "name": "C5:对角和=5", "rhs": 5,
       "terms": {"a": 1, "d": 1}}
    ]
  }]
}
```

- `terms` 支持任意非零整数系数（负系数等价于减法，求解器含负系数传播测试）；
- `cell_bounds` 可给单个格子收紧区间，缺省取 `[lower, upper]`；
- `state` 取值见上表；`requests` 按 `order` 串行裁决并把通过者落账。

## 求解器原理（全部整数运算）

1. 每个格子维护闭区间整数域 `[lo, hi]`；
2. 对等式 `Σ coefᵢ·xᵢ = rhs`，用其余格子的极值折算目标格允许的新上下界
   （盒一致性传播），系数为负时翻转不等号，整除分别向上/向下取整；
3. 传播到不动点后选区间最窄的未定值格（MRV），把区间划分为
   `[lo,mid-1] / {mid} / [mid+1,hi]` 递归回溯，划分无重叠无遗漏；
4. 叶子节点逐条约束精确整数校验；
5. 小表走穷举快速路径，大表走单调谓词二分求 min/max；节点超预算抛
   `BacktrackLimit`，引擎据此 fail-closed。

测试中 `SolverTests` 对 5 条约束的全部 32 个子集，逐一比较传播/回溯求解器与
独立笛卡尔积暴力枚举的可行性结论，并核对 min/max 投影与见证表，保证两条
代码路径结论一致。

## 限制与边界

- 约束形式为线性整数等式；区间传播不保证对任意约束系统直接弧一致，完备性由
  回溯搜索保证；
- 暴力枚举与穷举快速路径只适用于小表，大表自动切换二分路径并受 `node_limit`
  保护，预算内无法定论时否决而非放行；
- 台账为进程内状态，持久化可在应用层把 `records` 序列化后经 `jsonio` 重建。
